# Навантажувальні сценарії k6 для FilmArchive

## 1. Файли

- `filmarchive.js` — основний сценарій: 10 хвилин, 1 запис і 9 читань, для завдання 2 та порівняння кешу.
- `queue.js` — додатковий сценарій async API/черги, для бонусного завдання 6.
- `results-*.json` — локальні збережені результати (ігноруються Git).

## 2. Передумови

1. Docker Desktop запущено.
2. `api`, `db`, `redis`, `worker` працюють, наприклад через `docker compose -p film_archive_lab2 ps`.
3. `http://localhost:3001/api/health` відповідає `healthy`.
4. Grafana k6 встановлено: `k6 version`.

Якщо у Windows новий PowerShell не знаходить `k6`, додайте `C:\Program Files\k6` до User PATH і перезапустіть VS Code. Перезавантаження комп'ютера зазвичай не потрібне.

## 3. Основний сценарій

```powershell
cd C:\int\film_archive
k6 run `
  -e BASE_URL=http://localhost:3001 `
  -e VUS=10 `
  -e RUN_ID=local01 `
  --summary-trend-stats="avg,min,med,p(90),p(95),p(99),max" `
  --summary-export=loadtest/results-local01.json `
  .\loadtest\filmarchive.js
```

| Змінна | Значення за умовчанням у коді | Пояснення |
|---|---|---|
| `BASE_URL` | `http://127.0.0.1:3000` | Адреса API; у локальних командах явно задаємо `:3001` |
| `VUS` | 40 | Цільова кількість користувачів; для локальних вимірів **явно** задаємо 10 |
| `RUN_ID` | `lab2` | Унікальний ідентифікатор прогону та логінів |
| `PAUSE` | 0.15 | Пауза між ітераціями у секундах |

Фази: 3 хв збільшення 0→N, 5 хв N, 2 хв зменшення N→0. Для кожної ітерації виконуються 1 POST і 9 GET, а реєстрація/вхід відбуваються для кожного VU на початку.

## 5. Перемикання кешу

Перевірити поточний стан:

```powershell
docker compose -p film_archive_lab2 exec api printenv CACHE_ENABLED
```

Для зміни `CACHE_ENABLED` відредагувати `.env` та перевідтворити **тільки API та worker** (MySQL volume не видаляти):

```powershell
docker compose -p film_archive_lab2 up -d --force-recreate api worker
```

Перед кожним окремим прогоном бажано зберігати копію конфігурації й фіксувати вимірюваний стан. Redis лишається потрібним для черги та ідемпотентності навіть за вимкненого кешування читань.

## 6. Асинхронний сценарій

```powershell
k6 run -e BASE_URL=http://localhost:3001 -e RUN_ID=queue01 .\loadtest\queue.js
```

У поточному `queue.js` налаштовано **5 VUs на 2 хвилини**. Він перевіряє відповідь 202 та можливість звернення до `jobs/:jobId`. Це **додаткова** перевірка і не замінює 10-хвилинний обов'язковий сценарій.

## 7. Хмарне тестування

Для AWS після розгортання задається `BASE_URL=http://<ALB_DNS>` (реальний ALB DNS), а N підбирається до **фактичного** scale-out під час сталої фази. Після кожного тесту потрібно перевіряти scale-in до мінімуму та витрати AWS.

Не запускати навантаження на чужі адреси, старий уже видалений ALB або акаунт із нульовим доступним бюджетом.

## 8. Показники для звіту

Фіксувати: загальну кількість запитів, HTTP error rate, p50/p95/p99, requests/s, VUs, час UTC, стан кешу, кількість створених записів, MySQL load та CloudWatch графіки (для AWS-тестів). Показник k6 `read_success` **не є Redis hit ratio**.
