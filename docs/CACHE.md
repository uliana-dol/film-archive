# Кешування читань FilmArchive

**Завдання 5 — 2 бали.**  
**Код:** `src/lib/cache.js`, `src/lib/redis.js`, `src/controllers/mediaController.js`.

## 1. Мета

Зменшити кількість однакових SQL-запитів до MySQL при частому читанні каталогу. Найпоширенішою операцією є `GET /api/media` — отримання всіх записів конкретного користувача.

## 2. Реалізація cache-aside

Для кожного користувача застосовується ключ Redis `filmarchive:media:<userId>`.

```text
GET /api/media
     |
     v
CACHE_ENABLED=true?
     | так                        | ні
     v                            v
Redis GET(key)                 MySQL SELECT
     |
     +-- HIT  --> JSON -> HTTP 200
     |
     +-- MISS --> MySQL SELECT --> Redis SET EX 45 --> HTTP 200
```

Основні операції:

- **Cache hit:** Redis повертає готовий JSON, MySQL не викликається; лічильник `filmarchive:cache:hits` збільшується.
- **Cache miss:** застосунок читає `media_tracker` з MySQL, зберігає результат у Redis з `EX 45` і збільшує `filmarchive:cache:misses`.
- **TTL:** 45 секунд, що відповідає вимозі 30–60 секунд.
- **Інвалідація:** після успішного `POST`, `PUT`, `DELETE` видаляється ключ списку відповідного користувача.
- **Вимкнення:** `CACHE_ENABLED=false` змушує читати список з MySQL; сам Redis може залишатися потрібним для черги та ідемпотентності.
- **Статистика:** `GET /api/media/cache-stats` із JWT повертає `enabled`, `hits`, `misses`, `hit_ratio`, `ttl_seconds`.

Використовується спільний Redis: різні EC2 API можуть бачити той самий кеш. Якщо зберігати дані лише в пам'яті одного Node.js процесу, інші сервери отримували б незалежні версії списку та окремі TTL.

## 3. Реальні локальні вимірювання

Тестовий сценарій: 10 VUs, 10 хвилин, один POST + дев'ять GET в ітерації. За результатами двох запусків k6:

| Метрика | **Без кешу** | **З кешем** |
|---|---:|---:|
| HTTP-запити | 149 920 | 128 000 |
| HTTP-помилки | 0,00% | 0,00% |
| Середня швидкість | **249,84 req/s** | 213,29 req/s |
| Середня затримка | **15,22 мс** | 20,42 мс |
| p50 | **10,17 мс** | 11,97 мс |
| p95 | **40,35 мс** | 62,99 мс |
| p99 | **61,54 мс** | 102,00 мс |
| Кількість SELECT / навантаження БД | **Не виміряно** | **Не виміряно** |
| Redis cache hit ratio для окремого прогону | Не застосовується | **Окремо не виміряно** |

До запуску другого тесту було виконано `redis-cli MGET filmarchive:cache:hits filmarchive:cache:misses`. Результат: **25 599 hits**, **12 802 misses**, тобто сукупна частка hits — приблизно **66,66%**. Проте Redis-лічильники не обнулялися перед першим тестом, тому це **накопичена статистика**, а не чистий hit ratio саме 10-хвилинного прогону.

## 4. Аналіз порівняння

**Фактичний результат:** у другому тесті **без кешу** p95 був меншим на 22,64 мс, а пропускна здатність вищою приблизно на 17%. Це спостереження не варто замінювати вигаданим «кеш прискорив систему».

Чому так могло статися:

1. Сценарій постійно записує новий фільм. Після кожного запису кеш списку інвалідується, отже наступне читання часто стає cache miss і створює додаткові мережеві операції Redis.
2. MySQL на другому прогоні міг бути краще прогрітий (buffer pool, файловий кеш ОС).
3. Обсяг і склад тестових даних змінилися між прогонами: нові записи зберігаються в MySQL.
4. Продуктивність Docker Desktop може коливатися залежно від фонових процесів і стану комп'ютера.
5. При невеликому локальному навантаженні MySQL може відповідати достатньо швидко, щоб накладні витрати Redis були помітними.

Тому для коректної оцінки кешування варто порівняти навантаження на БД, відтворити однакові набори даних і виконати декілька повторень у різному порядку (кеш → без кешу та навпаки).

## 5. Як виміряти навантаження MySQL

Для локальної перевірки можна виміряти глобальний лічильник SELECT на початку й наприкінці кожного тесту. Найнадійніше спочатку увійти в оболонку контейнера MySQL:

```powershell
docker compose -p film_archive_lab2 exec db sh
```

Тепер **усередині контейнера** виконайте:

```sh
MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -N -e "SHOW GLOBAL STATUS LIKE 'Com_select';"
```

Вихід із оболонки — `exit`.

Різниця показника наприкінці й на початку — приблизна кількість SELECT за тест. Поділити на 600 секунд, щоб порівняти SELECT/с. Це **наближений показник**, а не заміна IOPS/CPU CloudWatch у хмарі.

Перед повторними тестами можна обнулити **тільки лічильники кешу**, не весь Redis:

```powershell
docker compose -p film_archive_lab2 exec redis redis-cli DEL filmarchive:cache:hits filmarchive:cache:misses
```

**Увага:** ця команда видаляє лише дві статистичні змінні, а не базу даних і не список завдань черги.

## 6. Актуальність даних

При TTL 45 секунд клієнт без інвалідації потенційно бачив би список, застарілий до 45 секунд. У поточному коді успішні `POST/PUT/DELETE` інвалідують кеш відповідного користувача, тож зміни зазвичай з'являються при наступному читанні.

Винятки: прямі зміни MySQL поза API, помилка Redis, одночасні cache miss і write, порушення узгодженості між процесами. Серед способів зменшення затримки — коротший TTL, версіоновані ключі, узгоджена інвалідація й блокування запитів на відновлення кешу.

**Cache stampede:** після завершення TTL багато паралельних запитів можуть одночасно отримати MISS і звернутися до MySQL. Застосовують single-flight / locking, jitter TTL, попереднє оновлення гарячих ключів.

## 7. Надійність і обмеження

У поточній навчальній реалізації помилка Redis може спричинити помилку endpoint читання. У production можна передбачити fallback до MySQL із контрольованим circuit breaker та метрикою збоїв кешу. Для ідемпотентності простий «пропустити Redis» небезпечний через ризик дублювання.


## 8. Підтвердження в хмарі та обмеження експерименту

Після розгортання в AWS перевірено авторизацію, отримання даних із MySQL і Redis через публічний ALB. Хмарний smoke-тест успішно прочитав статистику кешу, для контрольного користувача показав **1 hit, 1 miss, hit ratio 0,50**, а також зміг отримати окремий запис через API. Це **функціональна перевірка**, а не порівняльне навантажувальне вимірювання з/без кешу.

Механізм спискового кешу використовує окремий Redis EC2 і, на відміну від локального кешу Node.js, може обслуговувати кілька API-екземплярів. Раніше зафіксовані локальні Redis-лічильники **25 599 hits / 12 802 misses** демонструють накопичену частку влучань **66,66%**; не можна приписувати її лише одному k6-прогону, оскільки лічильники перед ним не скидалися.

**Контрольне вимірювання MySQL виконано:** порівняння з Redis і без Redis наведено в розділі нижче.

При відмові Redis поточний код не завжди переходить до MySQL, тому для production варто додати контрольований fallback для читань та окремі метрики несправності кешу.

## 9. Підсумок

**Функціональну вимогу cache-aside виконано:** TTL 45 секунд, читання Redis з переходом до MySQL на промаху, інвалідація після змін і спільний кеш для кількох EC2. Реальні послідовні локальні тести показали кращу латентність **без кешу** за даних умов; це важливий спостережуваний результат, а не помилка, яку потрібно приховати. Додатковий контрольований тест підтвердив зменшення кількості SQL SELECT на 99,85% під час повторних читань.
