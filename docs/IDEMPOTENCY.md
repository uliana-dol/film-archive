# Ідемпотентність операцій запису

**Бонусне завдання 7 — 2 бали.**  
**Код:** `src/lib/idempotency.js`, `src/lib/media.js`, `src/controllers/mediaController.js`, `src/worker.js`.  
**База:** таблиця `idempotency_records` у MySQL.

## 1. Мета

Під час нестабільного з'єднання користувач може повторити POST, бо не отримав відповідь на перший запит. Без захисту один фільм міг би з'явитися у каталозі двічі. Ідемпотентність гарантує, що повторення **того самого** запиту з тим самим ключем не створить повторний запис.

Ідемпотентність — властивість операції, за якої її повторне виконання не змінює кінцевий результат після першого успішного виконання.

## 2. Використання заголовка

Для `POST /api/media` та асинхронного маршруту можна передати HTTP-заголовок:

```http
Idempotency-Key: media_demo_2026_001
Authorization: Bearer <JWT_TOKEN>
Content-Type: application/json
```

Вимоги до ключа в коді: від **8 до 128 символів**, латинські літери, цифри, `_`, `.`, `:`, `-`. Без заголовка звичайний POST залишається дозволеним, але гарантія повторного результату через ключ не застосовується.

## 3. Алгоритм

1. Клієнт надсилає POST із `Idempotency-Key`.
2. Сервер обчислює SHA-256 fingerprint із HTTP-методу, шляху й тіла запиту.
3. Перевіряє Redis-ключ `filmarchive:idempotency:<userId>:<key>:result`.
4. Якщо результат існує й fingerprint збігається — повертає збережений **статус та JSON**.
5. Якщо ключ уже використано з іншим тілом — повертає **422**.
6. Для нового запиту створює Redis NX-lock на **60 секунд** і виконує запис.
7. Після успіху зберігає результат у Redis з `EX 86400` (24 години).
8. Звільняє блокування. Якщо одночасно прийшов такий самий ключ до завершення першого запиту — другий може отримати **409**, щоб повторити пізніше.

Схематично:

```text
POST + Idempotency-Key
          |
          v
      Redis GET(result)
       /            \
  існує            немає
    |                 |
перевірити hash    SET NX lock
    |                 |
повернути 201      INSERT MySQL
зі старим id         |
                   Redis SET result EX 86400
```

Додатково у MySQL використовується `idempotency_records` з унікальним первинним ключем `(user_id, idempotency_key)`. Це знижує ризик дублювання, якщо процес завершився між записом у базі й збереженням відповіді в Redis.

## 4. Як пов'язано з чергою

У `POST /api/media/async` клієнт отримує `202 Accepted` із `job_id`, хоча створення фільму завершиться пізніше. Для повторного запиту з тим самим `Idempotency-Key` сервер формує стабільний `job_id` із user ID і ключа, а worker додатково перевіряє статус завдання в MySQL. Це запобігає дублюванню навіть при повторній доставці SQS Standard.

## 5. Практична локальна перевірка

```powershell
cd C:\int\film_archive
powershell -ExecutionPolicy Bypass -File .\scripts\smoke.ps1 -BaseUrl http://localhost:3001
```

У наданому локальному журналі перевірка пройшла:

```text
3/5 Test Idempotency-Key: same result, one DB record
Idempotency OK, one media id=5
```

*Число `id=5` стосується конкретного локального прогону; в іншій базі ID буде іншим.* Інший прогін також підтвердив успішну перевірку, але зі своїм ID.

Окремі модульні тести підтвердили:

- Два однакові запити з одним ключем повертають однаковий результат, обробник виконується один раз.
- Повторне використання ключа з іншим тілом відхиляється.
- Паралельні запити захищені блокуванням Redis NX.

## 6. Демонстрація результату

Для більш наочного підтвердження бажано зробити **реальні** скриншоти:

1. Перший `POST /api/media` зі статусом **201** та створеним ID.
2. Повторення ідентичного POST з тим самим ключем — **той самий 201 і той самий ID**.
3. `GET /api/media` або SQL `SELECT` — у БД рівно **один** запис відповідного тесту.
4. За бажанням — статус **422** при зміні тіла з тим самим ключем.

Не публікувати JWT, секрети чи повні персональні дані на скриншотах.

## 7. Теоретичні пояснення

HTTP `GET`, `PUT` і `DELETE` ідемпотентні **за визначенням семантики**, хоча помилково реалізований сервер може порушувати цю властивість. `POST` загалом не є ідемпотентним, тому для повторюваних клієнтських запитів використовують окремий ключ.

**TTL 24 години** обмежує час повторного повернення збереженої відповіді Redis. Після завершення терміну ключу слід визначати правила повторного використання з огляду на резервний запис у MySQL та його очищення.

## 8. Висновок

Ідемпотентність підтверджена локально та AWS smoke-тестом (дві однакові відповіді й один запис); у Redis задано TTL 86400 секунд. В асинхронній схемі захист доповнюється контролем стану job в MySQL, що є важливим через повторну доставку повідомлень SQS.
